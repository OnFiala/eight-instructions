# Build 002 invariants and implementation target

These are design targets recorded before implementation, not verified results.

1. **Native ownership.** `programs/workspace.thread` will own names, source bytes, parsing, compilation, bindings, version publication, pins, rollback and reclamation. `programs/city.thread` will own roads, jobs, vehicles, routing and logical ticks. Both execute as Thread programs compiled by the real BF kernel. Host facilities remain generic execution, raw input/output, opaque images and rendering.
2. **Fixed resources.** Four named module slots, six reusable version slots, source up to 256 ASCII bytes per module/version, bytecode up to 128 words per version. One draft per module, active and one rollback root; explicitly pinned/dependency-referenced versions may survive. Capacity refusal is honest. Slot reuse is proven by hundreds of cycles, not capacity growth.
3. **Code and data lifetime.** Module arenas are separate from city data. Pure module code operates on its own bounded evaluation stack and receives values as arguments; it cannot mutate the city, source allocator or host. The city commits decisions only after successful bounded evaluation. Existing unrestricted Thread remains a trusted developer environment, not an isolation boundary against malicious workspace memory writes.
4. **Module profile.** Source is actual `: module-name ... ;` Thread syntax, with literals, arithmetic, comparisons, stack words, structured control flow and references to other typed modules. Module compilation is a Thread program running inside BF. It is not the bootstrap compiler and does not claim all general Thread words are safe policy words. Declared input/output counts, branch joins and bounded stacks are checked natively. Unsupported words and incomplete definitions are rejected.
5. **Binding.** Compiling a reference to another module binds its current exact version and acquires a dependency reference. Root calls select the active version at invocation. Explicit version handles retain old code until released. Publication does not retarget existing compiled dependencies or pinned handles. Module deletion is refused while external live references require its code.
6. **Atomic publication.** A candidate compiles into a free arena without changing the active or rollback version. On any failure its temporary storage/dependency references are released. Publication is allowed only outside module evaluation, between complete city ticks. Old active becomes the single rollback root; the previous rollback root loses its root and is reclaimed if unreferenced. Rollback swaps the two roots. A version serial never silently wraps into a valid stale handle.
7. **Simulation.** Three vehicles, bounded graph and jobs. A vehicle on a road retains that edge and its progress through code or road changes. New route decisions happen at nodes. Logical ticks are deterministic; rendering may interpolate only between emitted positions. Toll bridge stays open for both policy variants; closure is a distinct data experiment.
8. **Persistence and compatibility.** Whole-machine images retain workspace sources, compiled versions, references, city data and in-progress execution. New kernel hashes reject Build 001 images; preserve the original runnable artifacts and document use with the old release. No untested migration.
9. **Visual target.** Exact selected concept 1: dark 1487×1058 composition, dominant detailed isometric city, pale architecture, canal/bridges, lime routes, right module panel and bottom native event/memory strip. Rendered road connectivity comes from guest output. Reference is evidence, never a flattened interactive background.
10. **Release.** GitHub remains canonical, Sites existing project/address remains the public experience. Preserve Build 001 and its rollback deployment. Publish only after native, visual and reproduction verification; record source, artifact, tag and deployment separately.
